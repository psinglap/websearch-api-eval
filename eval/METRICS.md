# Metrics: definition, live measurement, standard, evidence

Each test is one agent search call (see `reports/Agent queries.md`): the provider gets the exact `query` string plus the same parameters for everyone: 10 results, full content where supported, the freshness window, and domains where supported. The same Claude model (`claude-opus-5-5`) then answers the `upstream_task` from the top 5 results. Every provider runs 10 queries × 3 repeats = 30 calls per use case. The grader model is fixed in `config/settings.yaml`, and promptfoo's model-graded checks use `defaultTest.options.provider`.

| # | Metric | Definition | How it is measured live (tool + file) | Industry standard it follows | Evidence produced |
|---|---|---|---|---|---|
| 1 | **Latency p50 / p95** | Time from sending the search request to receiving the full response | `time.perf_counter()` around the HTTP request only, on a persistent `httpx.Client`, after one discarded warm-up call per worker (`lib/search.py`). Returned to promptfoo as `latencyMs`. `asserts/latency_budget.py` (non-blocking) and the promptfoo `latency` assertion (weight 0) compare it with the budget: insurance 500 ms, finance/GTM 3,000 ms. p50/p95 are computed in `analysis/analyze.py` (numpy percentiles over the 30 calls). Provider-reported latency is kept alongside. Claude web_search has no separable search time, so its end-to-end time is used and labelled. | Artificial Analysis time per query ([methodology](https://artificialanalysis.ai/methodology/search-api)); You.com latency classes and p50/p95 ([evaluate-us](https://you.com/docs/evaluate-us)) | `metadata.search_latency_ms`, `provider_reported_latency_ms`, `end_to_end_ms` per row in the promptfoo export; raw JSON in `out/raw/` |
| 2 | **Accuracy (0–2)** | Answer compared with the answer key written at run time | `asserts/accuracy_simpleqa.py` uses the official SimpleQA grader template verbatim: A = 2, B = 0, C = 0. List answers can earn 1 through `asserts/partial_credit.py`. Tolerances (e.g. ±0.5%) are appended to the gold target. | SimpleQA ([openai/simple-evals `simpleqa_eval.py` @5e623c2](https://github.com/openai/simple-evals/blob/5e623c2b400af62a1278e23595f95b0853d7fe8a/simpleqa_eval.py)). Byte-identical to the template in You.com's harness. Tavily's differs only in indentation and the placeholder name. | Grade letter and raw grader text in `out/assert_log.jsonl`; `namedScores.accuracy_0_2` |
| 3 | **Correct "none"** | Says "nothing yet" when that is true, without citing stale pages as current | `asserts/correct_none.py`: a SimpleQA-style grader with gold = NONE under FreshQA **strict** rules. A stale or invented item presented as current fails, and a false premise must be rebutted. On queries that do have an answer, a false "none" is a miss. | FreshQA strict mode and false-premise questions ([Vu et al. 2023](https://arxiv.org/abs/2310.03214), [freshllms/freshqa](https://github.com/freshllms/freshqa)) | Grader JSON (`says_none`, `stale_or_hallucinated_as_current`) in `assert_log.jsonl` |
| 4 | **Freshness: % in window** | Share of returned results dated inside the scoring window (real-time 6 h, 24 h, 48 h, 168 h) | `asserts/freshness.py` with the date chain in `lib/dates.py`: provider date field → `htmldate` (extensive mode) on returned HTML → `htmldate` on the live URL (cached) → URL date pattern → undated. Undated results count as not fresh and are reported separately. | FreshQA; htmldate is the best-scoring open-source extractor ([evaluation](https://htmldate.readthedocs.io/en/latest/evaluation.html)) | Per-result date and `date_source` in `assert_log.jsonl` |
| 5 | **Newest relevant result** | Age in hours of the newest result judged relevant | Same assertion, using the relevance labels from metric 6 (cached per row) | You.com "time from publish to retrievable"; FreshQA | Same as 4 |
| 6 | **Precision@5** | Share of the top 5 results that are relevant to the information need, time window included | `asserts/precision_at5.py`: the grader labels each result 0/1, TREC-style. Missing results count as non-relevant. promptfoo `context-relevance` was **not** used: it scores context sentences, not per-result labels, and metric 5 needs the labels. | TREC binary relevance ([NIST](https://trec.nist.gov/data/reljudge_eng.html)); LLM assessors ([Thomas et al. 2024](https://arxiv.org/abs/2309.10621)) | Labels and reasons in `out/cache/relevance/*.json` and `assert_log.jsonl` |
| 7 | **Recall** | Share of the ground-truth items the provider returned | `asserts/recall.py` compares normalized URLs (`lib/urls.py`) with `ground_truth/{qid}.json`, which `ground_truth/pull_*.py` pulls at run time (GitHub, HN Algolia, Stack Exchange, Statuspage, NWS, NHC, SPC, OpenFEMA, SEC EDGAR). It also reports recall including URLs cited in the answer. | Set recall (DeepSearchQA-style list questions; classic IR recall) | Ground-truth JSON with raw API responses and sha256 in `ground_truth/raw/` |
| 8 | **Citation validity / faithfulness** | Each cited URL loads (HTTP 200) and supports the sentence that cites it. The answer as a whole is grounded in the retrieved context. | `asserts/citation_validity.py`: HTTP GET each `[n]` URL, then rapidfuzz-match the claim sentence against the live page and the returned text (threshold 70). Plus promptfoo `context-faithfulness` (metric `groundedness`), with `contextTransform` building the context from `context.metadata.results`. | ALCE citation quality ([Gao et al. 2023](https://arxiv.org/abs/2305.14627)); verifiability audit ([Liu et al. 2023](https://arxiv.org/abs/2304.09848)); RAGAS-style faithfulness | Status codes, match scores and claims in `assert_log.jsonl`; faithfulness reason in the export |
| 9 | **Content in one call** | The search call itself returned usable page text (> 200 chars), with no second fetch needed | `asserts/content_one_call.py` reads `metadata.content_in_one_call`. Parallel and Linkup return excerpts, which are flagged as such. Claude's page content is encrypted. | You.com bundled-content claim, measured directly | Characters of content in the top 5 per call |
| 10 | **Token efficiency** | Tokens passed to the answer model; tokens per correct answer | `asserts/token_cost.py` records `tokens_in` from `usage`. For Claude web_search this includes the search content Claude read. `analysis/analyze.py` divides total tokens by correct answers. | Tavily vs Claude tokens-per-correct comparison | `tokenUsage` per row in the export |
| 11 | **Cost per query / per correct** | Search price + LLM tokens (+ $10 / 1k Claude searches) | Search price comes from the provider response where available (Exa `costDollars.total`, Tavily `usage.credits`, Firecrawl `creditsUsed`), otherwise `config/prices.yaml` (source URL and date per line). LLM cost is tokens × list price. Analysis divides by correct answers. | Parallel and Tavily cost-per-correct reporting | `metadata.search_cost_usd`, `search_cost_source`, `llm_cost_usd` |
| 12 | **Reliability** | Errors, timeouts, rate limits, empty results, and in-body errors (HTTP 200 with an error inside) across the 30 calls | Providers catch every error and return it in metadata, so the row still counts. Claude's `web_search_tool_result_error` is read from the response body. `asserts/reliability.py`, then counted in analysis. Every anomaly is also auto-logged to `friction_log.csv`. | Exa's reliability claim about You.com, tested directly | `metadata.error_type`, `http_status`, `anomalies`; raw JSON |

**Statistics.** With 10 queries, results are reported per query: a provider "won 7 of 10", not "30% better". Accuracy carries a Wilson 95% interval computed over the 10 per-query majority outcomes, because the repeats are not independent samples. Paired win/loss against You.com uses an exact sign test, and a difference is called meaningful only at ≥ 6 wins with 0 losses. Ranks are computed over the 7 providers only; the You.com `knowledge=core` F1 variant is reported separately.
